# 儲存, 分支與恢復

新增參考資料, 預覽確認及候選階段恢復規則見[資料管理說明](../../sillytavern/docs/SPDB_FEATURES.md).

儲存點包含當前範圍的正文來源, 角色名單, 訪問控制, 記憶與情緒分析以及世界時鐘和賬本設定. 分支使用獨立範圍; 後續修改不會寫回原分支. 恢復會提升當前版本, 舊候選和遲到處理結果不能繼續提交. 未完成分析的來源仍須重試, 儲存點不會把它們變成處理成功.

酒館面板提供"儲存點, 撤銷與分支": 建立命名儲存點, 讀取列表後恢復, 或撤銷最近一次有儲存點的操作. 建立新分支會從當前狀態複製, 切換已有分支時用它的受管正文替換聊天內另一分支的受管正文; 另一分支仍儲存在資料庫中, 切回時重建. 原聊天中不由 XLDB 管理的內容不屬於儲存點.

刪除來源後, 與它有關的舊儲存點會移除; 當前刪除規則仍可讀取時, 普通舊備份或舊儲存點不能恢復該來源及其影響. 資料庫及刪除規則均丟失的災難恢復有下述明確限制. 編輯, 訪問設定, 偏好糾正和世界設定仍可通過有效儲存點撤銷. 此規則作用於執行刪除的範圍; 已經建立的其它獨立分支如也要清除, 應在相應分支處理.

受管檢索表隨刪除清理; 清理失敗時保留待處理記錄, 重新同步或重試後臺處理會繼續完成. 權威庫中的來源正文, 分析和相關糾正記錄會移除或清空. 這是應用層刪除, 不承諾擦除SQLite空閒頁,LanceDB歷史檔案, 使用者匯出, 舊備份或外部模型服務紀錄.Agent檔案宿主會清理已結束任務的請求與結果; 沒有可識別任務回執的檔案不會擅自刪除.

正文恢復過程中斷時重新綁定同一聊天, 以資料庫中的狀態重新載入正文; 不要手工刪除聊天後設資料中的恢復標記. 換聊天后必須重新綁定.Agent 對應操作見 [Agent 介面](../../companion-agent/docs/AGENT.md).

撤銷或恢復後若提示"檢索清理待重試", 正文與權威狀態已經提交; 點選"同步更改"繼續清理, 不要重複撤銷. 核心重啟,Agent CLI啟動及下一次檢索會先續做已登記的清理任務; 清理完成前不會用舊索引生成.

## 資料庫備份

在專案根目錄執行. 資料庫, 備份及恢復臨時檔案必須位於該安裝目錄的 `.local/` 下. 以下為預設酒館路徑,Agent 請替換為實際使用的 `.local/agent/data/authority.sqlite`.

```powershell
node tools/backup.mjs create .local/data/authority/xldb.sqlite
```

命令使用 SQLite 一致快照, 可在當前核心執行期間建立備份. 結果返回備份目錄及含 SHA-256 的 manifest; 備份包含資料庫中的私密正文和角色狀態, 請按使用者資料保管, 不要作為診斷紀錄公開.

恢復前停止使用這個資料庫的所有 XLDB 核心,Agent 程序(含 `node companion-agent/adapters/cli.mjs daemon stop --data-directory 資料目錄` 停止的常駐 daemon; 它仍存活時 `restore` 與 `recover` 會以 `agent_daemon_active` 拒絕), 然後執行:

```powershell
node tools/backup.mjs restore .local/backups/實際備份目錄 .local/data/authority/xldb.sqlite
```

恢復會核對備份雜湊, 表結構與 SQLite 完整性, 再合併當前庫已刪除來源的墓碑, 使普通舊備份不能復活當前已經刪除的內容. 相關派生狀態和不安全儲存點隨之失效. 原備份不修改; 恢復前資料庫及其輔助檔案移到返回的 `recoveryDirectory`. 恢復完成後重新啟動核心, 綁定聊天並檢查狀態; 檢索索引由有效來源重建.

程序保護標記使正在使用的資料庫拒絕恢復, 報錯 `backup_database_active`. 不要在服務仍執行時移除標記. 若程序恰好在初始化保護目錄時被強制結束,`<資料庫路徑>.xldb-guard/active/owner.json` 可能缺失或不完整, 此時不能自動確認所有者; 先確認所有使用該資料庫的程序確已停止, 保留該 `active` 目錄副本, 再手動將它改名為故障留檔, 之後重試. 正常的已退出程序標記可自動回收.

當前備份不包含模型連線憑據, 角色卡, 世界書或整個酒館安裝. 私有連線設定須單獨保管; 酒館原生聊天檔案由酒館自己的備份機制保護. 恢復命令不會自動修復外部酒館檔案.

## 資料庫丟失或損壞

正常庫回滾仍使用 `restore`. 資料庫丟失時, 使用獨立新路徑執行:

```powershell
node tools/backup.mjs recover .local/backups/實際備份目錄 .local/recovered/authority.sqlite
```

`recover` 先核驗備份, 再寫新路徑; 目標若是已受本專案保護的損壞庫, 會先保全原db/wal/shm檔案. 目標是有效資料庫時拒絕, 不以災難恢復覆蓋正常資料. 返回 `recoveryDirectory` 為保全位置, 新路徑時為null.

返回 `deletionRules: target` 表示合併了目標仍可讀取的刪除規則;`backup_only` 表示只能恢復到備份時的狀態,**無法保證保留備份之後的刪除**. 原資料庫及其規則均不可讀時, 程式不會編造後續刪除歷史. 請按這一範圍核對恢復結果, 再將宿主指向新庫. 恢復過程中斷的舊檔案保全目錄須留存, 直到新庫及宿主正文確認一致.


## Agent 主動訊息已傳送但後臺整理失敗

主動訊息只由 Agent 伴侶入口投遞; 酒館沒有主動陪伴, 也不再寫入主動訊息. 宿主經 `node companion-agent/adapters/cli.mjs run` 的 `companionClaim` 取得正文, 在宿主會話傳送後以 `companionReceipt` 回報結果. 已傳送回執和宿主訊息獨立保留. 回報後若後臺整理失敗, 用 CLI `operation: retry` 重試該來源的失敗階段; 不要重新生成或重發主動訊息. 重試成功後, 原訊息繼續使用相同來源和投遞標識. 宿主寫入結果未知時回報 `unknown`, 先在宿主會話確認訊息是否存在, 再用 `reconcileCompanion` 按實際情況回報已傳送(附宿主訊息 ID)或未傳送; 不能將未知狀態當作未傳送自動重試. 經常駐 daemon 時這些投遞操作不排隊, 細節見 [Agent 介面](../../companion-agent/docs/AGENT.md).

承諾記錄, 定向關係, 畫像來源與初始化出處隨權威資料儲存. 自然模糊是當前有效來源和對應時鐘上的派生投影, 撤銷複習來源會撤銷其重新整理效果. 主動性授權, 聯絡控制, 已傳送回執及使用者畫像糾正的恢復邊界按各模組的獨立使用者控制規則處理, 不隨劇情重放而重複投遞.
