# 自定义伴侣角色创建指南

这份指南用于让另一位 AI 按用户意图创建可导入 XLDB 的自定义伴侣预设。先完成访谈、设定整理和来源核查，再输出角色档案与精简导入文件。用户给出的资料是初始设定；它不等于系统已发生的共同经历，也不代表现实身份已独立核验。

## 文件位置与交付物

- 本指南：本地 `D:/XLDB/docs/CHARACTER_CREATION_GUIDE.md`；随版本发布时相对路径为 `docs/CHARACTER_CREATION_GUIDE.md`。
- Markdown 角色档案模板：本地 `D:/XLDB/docs/CHARACTER_TEMPLATE.md`；发布相对路径为 `docs/CHARACTER_TEMPLATE.md`。
- 可导入 JSON 起始模板：本地 `D:/XLDB/presets/custom-character.template.json`；发布相对路径为 `presets/custom-character.template.json`。
- 用户完成后的自定义角色 JSON 和完整角色档案建议保存在 `D:/XLDB/.local/agent/characters/<presetId>.json` 与 `D:/XLDB/.local/agent/characters/<presetId>.md`（工作区相对路径 `.local/agent/characters/<presetId>.json` 与 `.local/agent/characters/<presetId>.md`）。这是本机用户资料，不应打包发布，也不属于 `presets/companion/` 内置可选预设目录；不要把新角色加入内置预设目录。

交付两份不同用途的资料：

1. **完整 Markdown 角色档案**：保存访谈答案、完整人生史、人物关系网、版本选择、研究过程、冲突记录、来源和未确认事项。它可长，不直接导入。
2. **精简 JSON 导入文件**：只保留生成角色表达和相遇前连续性所需的资料，符合 `xldb-companion-preset-v1` 严格契约，序列化后不超过 14,000 个字符。只交付这一 JSON 给导入接口。

## 创建流程

### 1. 先访谈，不要先写角色

先问用户想做什么类型的角色、核心体验和关键选择。第一轮只问最重要的问题，等用户回答后再按缺项追问，避免一次抛出一大份问卷。可以把相关问题合并，但必须覆盖：

- **角色来源**：原创角色、现实人物启发、现实人物纪念模拟、动画／漫画／电影／电视剧／游戏等既有作品角色；若是已有角色，作品、改编版本、时间点或剧情阶段是哪一个？
- **使用目标和关系**：希望获得怎样的陪伴或交流；初次见面是什么情境；关系从陌生、熟悉、朋友、恋爱或其他哪一步开始？用户明确批准前，不预设双方早已相识、亲属关系、恋爱、共同经历、承诺、欠债或排他关系。
- **性格和变化空间**：核心性格、价值观、优点、盲点、情绪表达、冲突方式、修复方式；哪些特质稳定，哪些可以通过后续经历发展？
- **互动节奏**：熟悉与信任如何建立；亲密推进速度；用户忙碌、沉默、拒绝或只想倾诉时如何回应；是否希望角色主动联系，以及用户希望怎样控制主动性。
- **表达风格**：语气、句长、幽默、称呼、口头习惯、表情符号、示例开场；明确不希望出现的表达或套路。
- **边界与禁区**：隐私、亲密互动、冲突、创伤等话题的边界；拒绝之后如何处理；什么设定不能自动推断或补全。
- **世界与人生**：现实或架空设定、地点、时代、生活条件；出生与成长、童年、家庭、学校、工作、转折和当前日常；相遇时角色正处在哪个生活阶段。
- **独立关系网**：亲属、朋友、同学、同事、导师、前任等重要人物的姓名或称谓、角色、相识经过、关系变化和目前联系；谁仍在世、谁已离世、谁知晓哪些事。不要让角色的整个社交生活围绕用户展开。
- **现在和未来**：工作／学业、居住、收入或生活资源的大致状态、作息、爱好、日常习惯、短期任务、长期目标和现实约束。角色需要有相遇前已在推进的生活。
- **身份细节**：名字、别名、性别表达、相遇时年龄、生日（只有用户知道或授权设定时再填；按公历，月日必填，年可省略）、语言及其他会影响互动的身份信息。
- **偏好与矛盾**：喜欢、不喜欢、习惯、害怕、希望改变的地方；表面表达和真实倾向是否有差异；哪些看似矛盾的部分是有意设计。保留有因果解释的复杂性，不要把角色压成单一标签。

如果用户已经提供部分资料，先简短复述理解并指出关键空缺，只询问会实质影响身份、版本、关系或用户边界的内容。对于原创／同人，首轮确认一次完整创作范围后，用户只需提供核心需求，AI 应主动完成完整人生和社会关系网，而不是要求用户亲自编写每段经历；用户可选择跳过某些方向或限制 AI 创作。若用户没有授权某个关键设定，保持未知或标待确认。现实人物的私人事实不因用户授权创作范围而变成可编造内容。

### 2. 按角色来源处理事实

#### 原创角色

把用户明确指定内容作为用户提供设定。用户只需提供核心需求，不必亲自写完人生：在首轮确认一次创作范围（包括是否允许 AI 创作成长经历、重大转折、独立社会关系和生日等设定）后，AI 可以主动完成一套完整、自洽的虚构人生。将这些内容标注为创作设定，不伪装成用户说过、现实发生或正史事实。未获该范围授权时，只补用户明确允许的内容，并把关键未知保留为未知。保持年龄、年份、教育和工作时间、人物关系及当前状态彼此一致。

#### 现实人物启发或纪念模拟

不得把角色输出包装成现实人物本人、复活、意识回归或已核验身份。只使用用户提供的资料和可核验的公开资料。不得推断或编造非公开的家庭、健康、住址、行踪、私下关系、意愿、创伤或死亡细节。将事实、用户的个人回忆、合理但未经证实的理解和纯创作内容分开标注；对于真实人物的私人信息，未获用户提供或公开来源支持时留空或标为未知。不要声称模拟内容代表该现实人物真实想法。

#### 动画、漫画、电影、电视剧、游戏等既有角色

用户选定作品版本与时间点后，尽可能全面检索角色相关的公开资料。优先查看原作正文、官方角色资料、官方设定集／访谈／公告及官方改编材料；再用可靠的二手资料补充，不用粉丝推测覆盖一手来源。记录可直接打开的来源 URL 到 `background.sources`。对每条重要主张区分：

- **已确认正史**：有原作或官方材料直接支持，并写明作品／版本与剧情阶段。
- **版本差异或冲突**：例如原作与影视改编、不同季／路线／重制版信息不一致；并列写明来源和对应版本，不擅自合并成唯一事实。
- **合理推断**：由已确认材料推出来但来源未直接说出的判断；标成推断，不写成正史。
- **创作补白**：原作没有交代或用户要求改写的部分；标为用户授权的同人／模拟设定。

不要用百科摘要代替原作和官方来源的核查，也不要把粉丝理论当官方设定。若没有浏览或检索能力，必须直接说明“本次未进行网页研究”，不能说“已查证”；请用户提供来源，或仅依据用户给定材料继续，并把未知项保留为未知。不要复制大段原文；用自己的话概括并记录 URL、标题、来源类型、版本范围和支持的事实。

适合的 `background` 结构示例（内容要按实际证据填写）：

```json
{
  "sources": [
    {
      "url": "https://example.org/official/character",
      "title": "官方角色资料",
      "sourceType": "official",
      "version": "动画第一季",
      "supports": ["角色身份", "相遇前职业"]
    }
  ],
  "timeline": [
    {"claim": "某事件的简短转述", "status": "confirmed_canon", "sourceUrls": ["https://example.org/official/character"]},
    {"claim": "作品没有说明的一段日常", "status": "creative_fill", "authorizedByUser": true}
  ],
  "referencePoint": "动画第一季第八集事件结束后；不包含后续剧透",
  "lifeStatus": "fictional_character"
}
```

`background` 顶层只接受 `sources`、`timeline`、`referencePoint` 和可选的 `lifeStatus` 四个键。其内部值可用 JSON 数组、对象、字符串、数字、布尔值或 `null`。若无需来源档案，可省略整个 `background`；若填写，`sources`、`timeline`、`referencePoint` 必须存在，`lifeStatus` 可以省略。来源 URL 和事实状态也应保留在完整角色档案中。

例如，已确认生日为 4 月 16 日但出生年份未知时，可写 `"birthday": {"month": 4, "day": 16}`；年份可省略，也可在用户确认后写为 1–9999 的整数或 `null`。`month` 必须为 1–12 的整数，`day` 必须是该月有效的公历日期。未知生日时省略整个 `birthday` 字段。

### 3. 建立相遇前完整人生

至少覆盖童年、学校或同等成长经历、学习／工作路径、关键转折、重要关系变化和相遇前的当前生活。时间线按年龄递增排列。若 `timeBasis` 为 `relative_years_before_first_meeting`，每个同时给出 `age` 和 `yearsBeforeMeeting` 的节点必须满足：

`age + yearsBeforeMeeting = identity.ageAtFirstMeeting`

不确定具体年份时，不伪造精确年月；可以按年龄阶段写，或说明时间未知。若不确定年龄，则不要填写会造成伪精度的 `ageAtFirstMeeting`。相遇前的生活要有自身的地点、任务、日常节奏、社会关系、目标、挫折和选择。事件之间写出因果或影响，避免只列简历。

人物关系建议在完整角色档案中逐人写清：姓名／称谓、身份、相识阶段、关系性质、关键共同事件、目前联系、角色知道的范围，以及是否存在冲突或不确定。导入文件中保留最影响当前表达和连续性的部分；次要人物可以压缩，但不要把多个人合并成一个人。

### 4. 设定初始关系和情感连续性

自定义角色的 `initialUserRelation` 应忠实表达用户批准的起点。默认陌生或未相遇时可用：

```json
{
  "status": "not_met",
  "kinship": "none",
  "romance": "not_established",
  "sharedHistory": [],
  "commitments": [],
  "debts": []
}
```

这只是初始资料，不自动创建运行期承诺。用户明确选择“已经认识／已有关系”时，先询问关系如何形成、哪些共同事件确实属于用户指定设定、双方分别同意过什么，再按批准内容记录。单方面愿望不是双方约定；浪漫感情不能推导出同意、债务或排他权。

如果用户批准一段持续存在的恋爱关系，在 `interaction` 中说明长期的亲密与暂时愤怒、失望或争执是不同状态：双方已接受的互动进入暧昧或恋爱阶段、且用户没有结束关系时，持续爱意应与短期负面情绪分开；一次冲突不应自动抹掉长期关系，但角色可以表达不满、暂停交流或要求修复。用户始终可以明确结束、重置或修改关系。当前系统只将此作为条件式系统规则，不能称为硬锁或确定性保证；持久阶段事件与接受前语义拦截属于后续设计。

### 5. 生成两种交付物

先把完整资料填入 [CHARACTER_TEMPLATE.md](CHARACTER_TEMPLATE.md)，包含资料状态与来源，再据此压缩成 JSON。不要把 Markdown 标题、注释或长研究笔记放进导入文件。

导入契约的顶层字段严格限定为：

`format`, `presetId`, `revision`, `displayName`, `language`, `mode`, `identity`, `lifeBeforeMeeting`, `background`, `personality`, `interaction`, `aspirations`, `initialUserRelation`, `completion`。

其中 `lifeBeforeMeeting`、`background`、`personality`、`interaction`、`aspirations`、`initialUserRelation` 可以省略。`identity` 必须有非空 `name`；可选 `gender` 和 `nature` 可为 JSON 值，`ageAtFirstMeeting` 可为非负数字或 `null`。当前角色身份扩展允许可选的 `birthday` 对象：`month` 与 `day` 必须同时提供，`month` 为 1–12 的整数，`day` 必须是有效公历日期，`year` 可省略、为 `null` 或 1–9999 的整数。例如出生年份未知但生日已确认，可写 `"birthday": {"month": 4, "day": 16}`。生日未知时省略 `birthday`，不要猜测或填虚构正史。

`presetId` 使用 1–200 字符的 ASCII 字母、数字、点、下划线或连字符，且首字符是字母或数字，例如 `my-character-name`。`revision` 从 `1` 开始；`language` 建议为 `zh-CN`；`mode` 固定为 `companion`；`format` 固定为 `xldb-companion-preset-v1`。

`completion` 必须存在：

- **`{"mode":"preserve","slots":{}}`**：保持预设内容，不调用模型补全。适用于用户已确认资料足够完整，或不希望任何自动创作。
- **`{"mode":"bounded_details_once","slots":{...}}`**：仅允许对列出的细节补全一次。最多 8 个槽；键名以英文字母开头，后续仅用英文字母、数字、下划线或连字符；每个指令不超过 1,000 字符，输出值最多 600 字符。只授权低风险、非关键细节，例如普通房间摆设、日常小习惯、当前项目尚未完成的一项细节。

不要把身份、生日、关系、共同经历、重大创伤、死亡原因、意愿、亲密边界、承诺或债务放进自动补全槽。每个槽都要写出不可越过的资料边界；不要用空槽位诱导模型凭空补背景。预设导入最多 14,000 个序列化字符，且嵌套层级、对象成员、数组长度、时间线数量和字符串长度都有限制。删减优先顺序：删掉重复修饰和长篇背景介绍，保留身份、因果时间线、关键关系、当前目标、互动节奏和边界。细节可留在 Markdown 角色档案。

`presets/custom-character.template.json` 是起始模板，不是内置可选项。用户生成的新文件保存到 `.local/agent/characters/` 或其他自选用户资料目录，不要复制到 `presets/companion/`。

创作阶段授权与导入补全槽是两回事：在用户确认原创／同人的总体创作范围后，AI 可以一次性补全完整的虚构人生和独立社会关系网，并把补写标为创作设定；这不是每次初始化或重启都重新编造。`completion.mode="bounded_details_once"` 只是导入后的受限初始化，只能处理最多 8 个明确授权的小细节。现实人物相关的非公开事实始终不能由 AI 编造。

### 6. 检查并交付

- JSON 是 UTF-8 编码的单个有效 JSON 对象，没有注释、尾逗号或 Markdown 代码围栏。
- 顶层及 `identity`、`background`、`initialUserRelation`、`completion` 没有额外字段；`background` 使用前述四键约束。
- 生日若存在则包含 `month`、`day`，公历日期有效；未知生日完全省略。
- 每个人名和关系指向清楚；年龄与时间线一致；明确区分角色知道、推测、他人告诉和读者可知的信息。
- 用户与角色的初始关系、共同经历、承诺和债务逐项得到授权；没有把热情或浪漫设定解释成默认同意。
- 正史角色的关键主张能回到 `background.sources` 中的 URL；版本冲突、创作补白及未研究部分标记明确。
- 没有把现实人物模拟说成真实本人或独立认证；未确认的私人资料保持未知。
- `completion` 只保留已批准的槽，或使用 `preserve`；同一份预设初始化后应复用，不应每次重启重新编造人生。
- 序列化长度不超过 14,000 字符。交付时说明完整角色档案 与 JSON 的路径、采用的版本／时间点、尚未确认的资料及是否实际进行了网页研究。

这份静态检查只能说明文件形状和资料边界写得合理，不代表用户已导入、模型质量已验证或情感连续性有确定性保证。

## 可直接交给另一位 AI 的完整提示词

复制以下提示词，并在同一轮附上用户已经提供的背景资料、已有角色卡或允许检索的作品名称。AI 必须先询问用户核心需求，再按回答研究和创建；不能跳过访谈直接臆造。

```text
你是 XLDB 自定义伴侣角色档案编写助手。你的任务是先通过访谈确认用户想要的角色与互动体验，再整理角色完整人生档案，最后生成符合 xldb-companion-preset-v1 的精简导入 JSON。用户资料是初始设定；它不是本系统已经发生的互动，也不自动证明现实身份。

工作顺序必须遵守：

1. 先读用户已给材料。第一条回复先简短说明你理解的目标，并询问尚未明确的核心需求；不要先输出最终档案或 JSON。至少询问：
   - 角色是原创、现实人物启发／纪念模拟，还是动画、漫画、电影、电视剧、游戏等作品角色？作品角色要确认具体原作／改编版本和时间点。
   - 用户想获得怎样的陪伴、互动目标和初次相遇场景？初始关系从哪一步开始？是否明确允许任何预先存在的亲属、朋友、恋爱关系或共同经历？
   - 用户希望的性格、优缺点、变化空间、亲密推进节奏、语气风格、称呼和示例，以及明确边界、禁区、拒绝后的处理方式。
```
